**Intent:** the simulated aircraft that reaches the RCH map also appears exactly once in REM, through RCH's team relay and shared encoders only.
**Expected outcome:** a REM user in the same RCH team as the app sees one marker named as simulated, at the position the hub relayed with the marker metadata; restarting the publisher or replaying a message never adds a second marker. The REM marker does **not** follow the orbit until the REM companion change C-REM-3 (D-6).
**Target-perspective output:** the REM user sees the aircraft on REM's map; the hub operator sees one marker, one origin and the relay records; the pilot sees the app's destination hash and team in the test build.
**Truth owner:** the simulator owns the aircraft state; RCH owns the canonical object, team membership, authorization and the relay to REM; REM owns its display; shared crates own every wire format.
**Contract boundary:** `r3akt-uas-app` → `r3akt-map-core::sensor_wire::encode_object_fields` (fields 3, 11, 13) and `r3akt-profile-rch` (field 9 create, unchanged) → `lxmf-runtime` in-process backend → RCH ingest → RCH `sensor_telemetry::relay` → REM.
**Cutover:** with a team configured, the fix message is the shared object message (fields 3, 11, 13) instead of 2a's field-13-only message; without a team the 2a message is kept (D-9). Only behind the `publish` feature, in the host tool and `simNet`.
**Displaced path:** 2a's field-13-only fix message, for publishers that have a team.
**Acceptance evidence:** REM screenshot with one aircraft marker named as simulated; beside it the lat/lon of the `mission.marker.created` payload the hub relayed and the hub's origin position at the same moment; hub store and relay trace (one marker, one origin, relay messages to the REM destination, dispatch rejections); the same count after a publisher restart, a replayed message and a REM force-stop and relaunch; RCH map, store and `/Sensors` compared with 2a.
**Kill criteria:** any field-3/11/13 map assembled in this repository instead of `encode_object_fields`; a second aircraft object in RCH or REM; the aircraft sent as the app's own field-2 position; anything received reaching a flight command; a default build containing the publisher; a REM change made from this repository; REM evidence described as tracking or as the aircraft's current position.

## What the hub and REM do (read at RCH `f5822210`, REM `0cfa422`)

- RCH relays an object update to REM only when the incoming message carries field 11 equal, byte for byte, to the lowercase UID of one of RCH's canonical colour teams (BLUE is `43341e5c822d99857fa6e8641f2ca9c0`), the sender is a member of that team, and each recipient is a team member whose announce marks it as REM (capabilities `r3akt` and `emergencymessages`). A team name such as "Blue", or an upper-case UID, relays to nobody without an error.
- Membership is matched by **`lxmf.delivery` destination hashes**: the hub records `reticulumd` announces without an identity hash (`r3akt-rch-server/src/lib.rs:2653`), so `canonical_identity_for_rem_source` falls back to the source delivery hash (`r3akt-rch-core/src/rem_team_directory.rs:81-91`), and REM recipients are found by their announce's destination hash (`:201-215`). Both the app and each REM are added to the team with `rns_identity` = their delivery hash.
- Every relay is re-authorized: `mission.content.write` for the app's delivery hash and the writer binding from the 2a `mission.marker.create` are still required; the create needs no field 11. On a fresh hub the create must arrive before the first object message, as in 2a.
- The hub rejects a whole message with a different fix at an already stored `fixAtMs` and silently ignores an older fix: fix times stay wall-clock, and the sending clock must not be behind the last fix the hub stored.
- With no sensors the field-3 entry is dropped by the hub's stream decoder, so only the field-13 fix is staged; the shared encoder's hard-coded `camera` appearance and datumless SID-2 altitude are carried on the wire but not stored.
- Relay dispatch re-checks that the queued snapshot is still current and drops it otherwise (`durable_broker/outbound.rs`, `sensor_telemetry.rs` `dispatch_allowed`); if dispatch lags behind 1 Hz fixes, relays can be dropped and REM shows nothing.
- **REM decodes neither field 3 nor the origin-fix event.** It shows the aircraft through the `mission.marker.created` event the hub puts in each relay until a relay to that REM is confirmed delivered, keyed by `object_destination_hash` (newest wins, no duplicate). REM therefore settles at the hub's position of the last relay that still carried the marker metadata, and stays there. The confirmation is stored per origin and REM destination: a REM that clears its data but keeps its identity never receives the marker again.

## Known limits accepted for 2b

- REM shows the aircraft at the relayed metadata position and does not follow it until C-REM-3 lands (D-6).
- The relay reaches only REM clients the hub operator has added to the same canonical team by delivery hash; REM does not join a team by itself.
- A REM whose relay metadata was confirmed delivered never receives the marker again if it loses it locally (clear data, local delete) while keeping its identity.
- Relays are dropped when hub dispatch lags behind the fix rate; the evidence records the rejections.
- The app still cannot read hub results (G-17): a refused or unrelayed message is visible only on the hub.
- REM shows the RCH symbol `drone` (G-19); the simulated mark travels in the marker name.

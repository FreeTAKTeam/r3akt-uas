# R3AKT UAS 0.1.0-alpha.1: tester notes and known limitations

An alpha for a small group of testers who fly under their own supervision. It is not release-qualified: milestone 6 has not started, no product milestone (2–6) has owner acceptance, and most features are **implemented but unproven**. [acceptance.md](../specification/acceptance.md) holds the status of every requirement; [issue #26](https://github.com/FreeTAKTeam/r3akt-uas/issues/26) tracks what is still open.

## Which APK

- **`dji4Net`**: the DJI SDK 4 build that publishes to an RCH hub. It is the build that flew. It is still a test build (D-4, amended by D-18). The release APK carries no hub address, destination or team: enter them on SETTINGS → HUB before MESH → START PUBLISH. (Debug builds take defaults from the `r3aktHubAddress`, `r3aktHubDestination` and `r3aktTeamUid` Gradle properties.)
- **`dji4`**: the DJI build without hub publishing.
- **`sim` / `simNet`**: the simulated aircraft, without and with publishing. Everything it shows is marked simulated.

Build the publishing variants with `-Pr3aktPublish=true`, for example `./gradlew -Pr3aktPublish=true :app:assembleDji4NetRelease`. The DJI builds need the `djiApiKey` Gradle property; release signing needs `r3aktReleaseStoreFile`, `r3aktReleaseStorePassword`, `r3aktReleaseKeyAlias` and `r3aktReleaseKeyPassword`. All of them live outside the repository (for example in `~/.gradle/gradle.properties`). Without the signing properties the release APK is unsigned.

## Setup on the hub

Every installed app has its own identity. The hub drops a team marker from an identity that is not a member of the team, without telling the app (G-24). Before flying:

1. Enter the hub address, hub destination and team UID on SETTINGS → HUB.
2. Start publishing once and read **App identity (destination hash)** on SETTINGS.
3. On the hub, grant that identity and **add it to the team** entered on SETTINGS → HUB.

## Shown on hardware

Only one combination has flown: a DJI Mavic Air 2 with its standard remote controller and a Pixel 7 (Android 17), two flights on 15 November 2026 ([first flights](../evidence/dji-net-first-flight.md)):

- take-off, landing and return home from the app;
- live flight values, flight modes and take-off-relative altitude;
- DJI accepting the photo/video mode buttons on the ground;
- markers placed from the app reaching the hub once the identity was in the team.

## Implemented but unproven

These have code but no captured evidence on an aircraft or end to end. Expect failures.

- Photo, video recording, gimbal down/level and the camera/gimbal controls in flight.
- Video preview in flight; RTMP streaming to MediaMTX (not run against a MediaMTX server; no WebRTC/HLS/RTSP viewing shown).
- Aircraft media listing and download (no aircraft card read yet).
- Receiving markers from REM and the hub onto the radar and map (host-tested only).
- Picture markers (issue #19): host-tested; no device, hub or REM run. Crops come from the live video frame, often below 1600 × 1200.
- The camera aim point on DJI builds (host-tested; not on an aircraft).
- Radar: shown on the emulator with simulated contacts; heading-up rotation only in fixture tests.

## Not built

- No video stream reference in RCH (UAS-VID-002) and no mission/team rights for playback.
- No on-device object detection (issue #17).
- No TCP/RNode mesh qualification or offline synchronization.
- No model/controller compatibility matrix beyond the one combination above.

## Rules testers should know

- Nothing received over the network commands the aircraft; flight commands are only the app's own buttons.
- Altitude is take-off-relative unless the aircraft reports otherwise, and is never shown as MSL, HAE or AGL.
- A marker is placed only from an aircraft fix at most 5 s old; with no current position the app refuses.
- While DJI's built-in simulator runs, the app publishes no aircraft position.
